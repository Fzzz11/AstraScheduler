### 3.1 TSan 全量 54 与 Reaper / Runtime State 析构

这里叠了两件独立的事。

**（a）finalization 测试上的 TSan 报告**

`Scheduler` 持有 `shared_ptr<Impl>`。最后一个 Scheduler Handle 若在所属 Worker 上销毁，不能在本线程 join 自己，于是走 orphan handoff（ADR-0008 / D-018）：把 Runtime State 的强引用交给进程级 Reaper Service（ADR-0011 / D-021），由协调线程调用 `reaper_cleanup_and_join()`。

关停完成是 Leader–Waiter 共享 Shutdown Completion。非 Leader 在 `shutdown_done_cv` 上等待，谓词读取 `Impl` 的 `packed_status`：

```419:422:src/runtime/scheduler.cpp
            shutdown_done_cv.wait(s_lock, [&status = packed_status] {
                return unpack(status.load(std::memory_order_acquire)).state ==
                       SchedulerState::Stopped;
            });
```

2026-08-31 WSL TSan（`build/wsl-gcc-tsan`，`TSAN_OPTIONS=halt_on_error=1:print_stacktrace=1`）已复现，分类为 **真生命周期缺陷**，不是 fence 误报，也不是跨测试残留。

复现命令与命中用例：

```text
./build/wsl-gcc-tsan/tests/astra_finalization_begin_test
./build/wsl-gcc-tsan/tests/astra_finalization_wait_test
```

- `test_R031_begin_does_not_wait_for_runtime_completion`（`tests/test_finalization_begin.cpp`）
- `test_R039_worker_calling_wait_throws_logic_error`（`tests/test_finalization_wait.cpp`）
- 第二次单独跑 `astra_finalization_begin_test` 仍报告 data race（至少 2 处）。

TSan 两侧：

- **写**：主线程 `Scheduler::~Scheduler`（`scheduler.cpp:1234`）把最后一个 handle 侧 `shared_ptr<Impl>` 降到 0，`operator delete` 释放整块 `Impl`（含 `packed_status` 与 `shutdown_mutex`）。
- **读**：Reaper 协调线程在 `reaper_cleanup_and_join` 的 `condition_variable::wait` 谓词里 `packed_status.load`（`scheduler.cpp:420`），当时持有 `shutdown_mutex`（该 mutex 在同一次 `~Scheduler` 的 `shutdown_sync` 里创建/使用）。

机制：

1. `register_runtime` 的 cleanup 是裸 `this`，不是强引用：

```181:183:src/runtime/scheduler.cpp
                [this] {
                    this->reaper_cleanup_and_join();
                })) {
```

2. `retained_state`（`shared_ptr<void>`）只在 Worker orphan handoff 时赋值。Handle RAII 关停路径不把 Runtime State 交给 Reaper 持有。
3. Finalization 已开始时，协调线程可在 Join Ready 后调用上述 cleanup。与此同时测试线程析构 `Scheduler`：非 Worker 上 `use_count()==1` 走 `shutdown_sync`（Leader，`scheduler.cpp:1227`），Reaper 已进入 `reaper_cleanup_and_join` 则走 Waiter。
4. Leader 发布 `Stopped` 并返回后，析构继续 `delete Impl`。Waiter 仍可能在谓词里读 `packed_status`，或仍持有即将被销毁的 `shutdown_mutex`。

谓词从捕获 `this` 改为只绑 `packed_status`，只修了多重继承下 UBSan 的成员调用类型；**没有**让 Waiter 的寿命短于 `Impl`。ASan/UBSan 全量 54 通过，只说明这条窗口在那些检测器下不易变成必现 UAF，不能用来否定 TSan 报告。

### 3.2 Global FIFO / EDF 改 lock-free

Local 无锁与 Global 无锁不是同一条规则。

Chase-Lev 只覆盖所属 Worker 的四条 Local priority band：owner 写 bottom，thief CAS top。跨 Worker、外部 submit、以及带 Deadline 的首次就绪工作仍进 Global Injection Queue。现行实现一把 `global_mutex_`：

- 普通任务与 resume：四条 `IntrusiveFifo`（侵入式链表，入队不再为节点分配）
- 带 Deadline 的非 resume：四条 EDF heap（`vector` + `push_heap`）

`publish`、`claim_global`、Immediate `cancel_unstarted` 的 Global 段都持这把锁。D-100 的 Global fallback 要求：**锁竞争允许，入队不得失败**。Local 扩容或 rebase 失败时，已接受任务必须还能无额外分配地进入 Global，不能因为再分配队列节点而丢失 Scheduling Reference。

把 Global 改 lock-free 等于新增生产队列，需要同时保持：

- 恰好一个 Scheduling Reference
- Immediate 下 resume 例外（R-059）与非 resume 预取消
- 外部 slot 在 claim 后释放
- EDF 与 FIFO 的 deadline burst 交替，避免饿死（ADR-0026 / ADR-0037）

这与 Local Chase-Lev（对照 Lê et al. 2013 portable 序）证明面不同。现行 Spec/决策把 Global 锁视为允许的正确性手段，而不是遗漏的无锁实现。未修订 D-100 与相关规则前，不得以「补测试把 mutex 测没」的方式开 TDD。

**下一步**：若产品上要做，先走决策台账 → Spec → Ticket。在那之前本文把它标为设计变更，不进入实现队列。

### 3.3 TSan 注解不是弱内存证明

生产 `ChaseLevDeque` 按 ADR-0028 / D-098 使用 `atomic_thread_fence`（push 的 release fence、pop/steal 的 seq_cst fence）。这是 C++ 内存模型里的序。

GCC TSan **不建模** `atomic_thread_fence`（编译时 `-Wtsan`）。没有旁路时，检测器会把 owner 写 cell、thief 读 cell 报成 data race，即使 fence 在标准里已经建立 happens-before。因此在 fence 旁增加 `__tsan_acquire` / `__tsan_release`，只改检测器的 happens-before 图，不生成 CPU 屏障，也不改变 `std::atomic` 的 memory order。非 TSan 构建里这两条调用为空操作。

本批步骤 C 把 `maintenance_` / `active_thieves_` 改成 seq_cst，修的是 C++ 序上的 store-load 窗口，依据同样不是这些注解。

因此：

- TSan 相关子集通过，只说明「检测器被教会看待这些 fence 之后，Chase-Lev cell 路径不再报警」
- 不能写成「已在弱内存模型下证明」
- ARM/弱内存证据仍是 portable 序对照，以及 native Linux AArch64 复核（ADR-0047 Tier-2）

**下一步**：在 ADR-0028 或 AST-074 Verification 中写明上述边界。不要删除注解（会让 TSan 对 cell 再报警），也不要新开「用代码证明弱内存」的 Ticket 却只改注解。

### 3.4 控制线程代 owner 写 bottom（拒绝方案）

Chase-Lev 的前提是 bottom 单写者：只有所属 Worker 的 `push`/`pop` 修改 `bottom_`。其他人只从 top `steal`（CAS `top_`）。ADR-0026 已写：**外部线程永远不写 owner-only deque**。

先前错误路径是 Immediate cleanup 在控制线程 `steal` 出 resume 后再 `LocalQueues::push()`，非 owner 写 bottom。A–E 的步骤 A 已改为：控制线程只做 thief 合法的 steal；resume 进入 Global FIFO；Worker 在 Immediate 下仍 `claim_global`，resume 因 R-059 例外继续 `execute()`。加锁 Local 可在 `locked_mutex` 下把 resume 留在 band 里，因为那条路径本来就不是 owner-only deque。

「代 owner 写 bottom」是当时想过、现已拒绝的替代修法，包括：

- 控制线程直接调用 `ChaseLevDeque::push()`（与已修 P0 同类）
- 在控制线程改 TLS / worker index 再 publish 到 Local（owner 可能同时 push，仍是双写者）
- 给 deque 增加「外部 push」特例（放弃单写者证明）

若将来一定要把 resume 送回 Local LIFO，只能让 **真正的 owner Worker 在自己的循环里** `push`，例如控制线程投递一条由 owner 执行的回写消息。那是新协议，需要新决策，不是把 P0 改回去。

**下一步**：不实现、不拆实现 Ticket。本文与前序计划第 6 节继续把它列为拒绝方案。
