# AstraScheduler 封装性审查与改进建议

状态：已进入实施；D-169、R-113～R-117、AST-057 已建立  
日期：2026-08-30

当前落地情况：

- 项目版本进入 1.1.0，v1.0 manifest 已恢复为发布 tag 的原始内容；v1.1 使用 semantic public contract。
- `TaskHandle` shared state、`Task` raw coroutine frame、Frozen Graph node storage、GraphRun completion callback 与 `AwaitHandshake` 已从普通 public surface 收回。
- 测试注入入口只保留在非安装的 `src/test_seam.hpp`；public tests 不再获得 `src/` include path，并新增 negative compile gate。
- TaskId/GraphRunId 由非安装的 `RuntimeIdentityAllocator` 统一分配并拒绝 overflow wrap/reuse。
- Graph 运行协议由非安装的 `GraphExecution` 作为唯一入口，`Scheduler::run_impl` 只负责委托。
- 后续若继续细化 `Scheduler::Impl`，只按 admission、timer、observability 等完整不变量拆分，不建立字段转发型浅层 wrapper。

## 1. 审查结论

AstraScheduler 的公共功能设计已经较成熟，`Scheduler`、`FinalizationControl`、`TraceCollector` 也具备深模块雏形；但代码层面的封装性目前只能评价为“中等”。主要问题不是缺少更多类或更多 PImpl，而是：

- Task、Coroutine、Graph 的内部状态与控制协议大量进入 installed headers；
- 测试 seam 与公共 Interface 没有严格隔离；
- API freeze 将 `astra::detail`、private 声明和 header 实现细节一并冻结；
- Graph 执行状态机、调度策略和观测逻辑集中在 `Scheduler::Impl`，内部知识缺乏 Locality；
- 一些带 `_internal` 名称的入口仍然是普通调用方可以直接使用的 public 成员。

改进目标应是形成少量深模块：调用方只学习稳定的生命周期和结果语义，复杂的 admission、Task 状态、Coroutine resume、Graph 依赖传播、Timer、Metrics 与 Reaper 协议留在各自实现内。

## 2. 评价方法

本审查使用以下标准：

- **Module**：具有 Interface 和 Implementation 的函数、类、包或纵向切片。
- **Interface**：调用方正确使用 Module 必须知道的全部事实，包括类型、状态约束、调用顺序、错误模式和性能语义。
- **Depth**：调用方每学习一单位 Interface 能获得多少行为能力。
- **Seam**：可以替换行为而不修改调用位置的接口所在位置。
- **Adapter**：在某个 seam 上满足 Interface 的具体实现。
- **Locality**：一个规则的状态、实现、测试和修改是否集中在同一处。

不建议为了“分层”而建立只转发字段或方法的浅 Module。只有当一个 Module 能吸收完整不变量、显著缩小 Interface，并让调用方不再重复理解内部协议时，拆分才有价值。

## 3. 已有良好基础

以下设计值得作为后续改造的参考：

- [`FinalizationControl`](include/astra/finalization.hpp) 通过很小的 Interface 隐藏进程级注册关闭、等待、升级和 coordinator join 协议。
- [`TraceCollector` / `TraceCapture`](include/astra/trace.hpp) 使用显式 capability 和 PImpl 隐藏 buffer、generation 与 producer 管理。
- [`SchedulerOptions`](include/astra/scheduler_options.hpp) 主要暴露稳定 policy，而不是 active-spin、deque capacity 等实现参数。
- [`SchedulerCapabilities`](include/astra/capabilities.hpp) 以不可变值对象报告事实，不提供控制内部 backend 的入口。
- `Scheduler` 最近已经采用 `Impl` 并将部分非模板实现移出 public header，方向正确，但尚未完成 Interface 收敛。

## 4. 主要发现与建议

### P0：API freeze 正在冻结内部实现

证据：

- [`tools/check_api_freeze.py`](tools/check_api_freeze.py) 对 installed header 做完整字节哈希，因此注释、private 区和模板实现的变化都会被当成公共表面变化。
- 该工具通过 `_ZN5astra...` 正则收集整个 `astra` 命名空间的动态符号，没有排除 `astra::detail`。
- 当前 golden manifest 有 131 个导出符号，其中 57 个包含 `astra::detail`。
- `v1.0.0` tag 之后的封装提交修改了 `scheduler.hpp`、`task_handle.hpp` 和 `tools/api_manifest/v1.0.0.json`，但项目版本仍为 1.0.0。同一个版本号因此可以对应不同 header 哈希和导出符号集合。

影响：

- 内部实现被反向当成稳定公共 Interface；
- 正常封装重构必须修改已发布 golden，或者被 freeze gate 阻止；
- exact-version package 无法区分两个不同实现的“1.0.0”；
- `R-110` 的 internal symbols hidden 与实际导出集合不一致。

建议：

1. 发布后的 manifest 必须不可修改，新版本生成新 manifest。
2. 使用 AST/声明级清单冻结 approved public Interface，不再冻结整个 header 字节。
3. 将检查拆成三个独立门禁：
   - documented source Interface；
   - observable semantic tests；
   - same-version shared-library implementation bridge。
4. 使用 linker version script 或显式 export allowlist，只默认导出批准的公共符号。
5. 对 consumer 模板确实需要调用的内部桥接符号单独分类；它们不应被描述为公共 source Interface。
6. 在继续封装改造前先确定 1.1 兼容迁移或 v2 breaking 策略，并修订 Decision Ledger、Spec 与 Tickets。

### P1：FrozenTaskGraph 暴露可变内部节点

证据：

- [`FrozenTaskGraph::NodeData`](include/astra/graph.hpp) 是 public 类型，包含 `unique_ptr<detail::TaskInvokerBase>` 和可变 options。
- `nodes_internal()` 是 public 方法并返回可变 `std::vector<NodeData>&`。

影响：

调用方可以在 `freeze()` 之后移动 invoker、修改 options 或破坏节点与边的一致性，使 “Frozen Task Graph” 的不可变和 single-shot 不变量无法由 Module 自身保证。

建议：

- 将 `NodeData`、`nodes_internal()` 移入 private；
- 只允许 `TaskGraph` 和内部 `GraphExecution` 消费节点所有权；
- 公共 Interface 仅保留 `node_count()`、`edge_count()`、`empty()` 以及确有调用价值的只读拓扑观察；
- 若 `edges()` 并非正式使用场景，也应考虑用更窄的只读遍历或完全移除。

### P1：Task 与 Coroutine 暴露可绕过 Runtime 的 capability

证据：

- [`TaskSharedStateBase`](include/astra/task_handle.hpp) 公开状态转换、mutex、condition variable、rescheduler、timer hooks、completion callback 和异常发布。
- `TaskHandle` 的 shared-state 构造函数是 public。
- `TaskHandle::shared_state_internal()` 返回可变内部状态。
- [`Task::handle()` 与 `Task::release_handle()`](include/astra/coroutine.hpp) 公开 coroutine frame 的原始所有权入口。
- `TaskPromiseBase::shared_state`、`AwaitHandshake`、`CoroutineResumeInvokerModel` 等实现协议位于 installed headers。
- [`GraphRun::add_completion_callback_internal()`](include/astra/graph.hpp) 虽带 `_internal` 名称，仍是正常调用方可使用的 public 方法；这与 R-078 排除 callback completion public Interface 的方向冲突。

影响：

- 调用方可以自行制造 TaskHandle、转移或泄漏 coroutine frame、修改 Task 状态；
- Namespace `detail` 和 `_internal` 只是命名约定，不构成访问控制；
- 第三方 awaiter 若依赖这些类型，需要同时理解 shared state、rescheduler、invoker、handshake 和 suspension 状态，Interface 几乎与 Implementation 一样复杂，是典型浅 Module。

建议：

1. 将 TaskHandle 的内部构造、`shared_state_internal()`、GraphRun callback 注册和 Task raw handle 操作改为 private。
2. 使用精确 friend 或一个最小内部 access object，而不是继续增加 public `_internal` 方法。
3. 将 `TaskSharedStateBase` 重构为 compiled `TaskControlBlock`，只保留最小状态机 Interface。
4. 模板层只保存结果 `T` 与 one-shot Callable 所必需的类型信息；等待、取消、Metrics、Timer 与 resume 路由交给 compiled control block。
5. 若正式支持第三方 Astra-aware awaiter，先通过决策流程设计一个小型 `ResumeToken`/`SuspensionRegistration` Interface；不要把现有 shared state 协议直接宣布为扩展 Interface。
6. 若不正式支持第三方 awaiter，则将当前相关测试改为 internal tests，并收回这些入口。

### P1：TaskId 分配策略位于 consumer header

证据：

- [`detail::allocate_task_id()`](include/astra/task_handle.hpp) 是 public header 中带函数局部静态原子的 inline 函数。
- `Scheduler::submit`、`try_submit`、`spawn` 和 `try_spawn` 模板直接调用它。

影响：

Task Identity 的分配行为发生在 consumer 翻译单元。多 DSO 或不同可见性组合下可能出现多个分配实例，使同一 Runtime 内的 identity 唯一性依赖编译器和链接器合并行为，而不是 Runtime State 自身。

建议：

- TaskId 必须由 compiled Runtime State 分配；
- 提交模板从 Runtime 获取一次 admission/identity transaction；
- transaction 同时承载 resolved priority、deadline、internal/external 分类和外部 slot rollback；
- 模板只负责构造类型相关的 result cell 和 callable model，不能拥有全局 identity 或 admission policy。

### P1：Graph 执行协议缺少自己的深 Module

证据：

- [`GraphRunSharedState`](../src/graph/graph_shared_state.hpp) 是公开字段的数据袋。
- `GraphRun` 的查询、等待、取消在 `src/graph.cpp` 中直接读写这些字段。
- [`GraphExecution`](../src/graph/graph_execution.cpp) 独立实现 admission、节点初始化、依赖释放、失败传播、Coroutine Node、deadline、Metrics 与 terminal publication。

影响：

- Graph 的一个规则通常要同时修改 `graph_shared_state.hpp`、`graph.cpp`、`scheduler.cpp` 和 coroutine 模板；
- Scheduler 必须理解 Graph Node 的全部内部状态；
- Graph 测试容易越过 Interface 检查原子字段，重构成本高；
- Graph Module 的 Interface 与 Implementation 没有形成清晰 seam。

建议建立内部深 Module `GraphExecution`：

- 输入：consumed frozen graph、resolved graph policy、admission lease；
- 外部 Interface：`start()`、`request_cancel()`、`wait()`、`wait_for()`、`report()`；
- 内部独占：节点状态、依赖计数、edge policy、失败传播、Coroutine Node ownership、terminal publication；
- Scheduler 只提供 Ready publication seam，不再直接访问 NodeEntry；
- 该 seam 有两个真实 Adapter：生产 Scheduler adapter 与确定性内存测试 adapter；
- 新测试通过 `GraphExecution` Interface 验证 observable outcome，替换直接检查内部字段的旧测试。

### P2：Scheduler 的 PImpl 仍是半封装且职责过密

证据：

- [`Scheduler::Impl`](include/astra/scheduler.hpp) 的前向声明位于 public 区，主要是为了方便实现文件中的非成员辅助函数访问。
- `src/runtime/scheduler.cpp` 当前约 2000 行；Graph execution、Worker loop 与 Runtime registry 已迁出，后续仍可继续围绕 ready queues 与 diagnostics 深化。
- `submit`、`try_submit`、`spawn`、`try_spawn` 的 policy resolution 与 transaction rollback 在 public header 中重复。

建议：

- 将 `Scheduler::Impl` 重新收回 private，或使用 internal header 中的 `RuntimeState`；
- 将重复的提交准备过程收敛为一个 compiled admission transaction；
- 按完整不变量而不是按文件大小抽取深 Module：
  - `AdmissionController`：准入、backpressure、slot lease 和 rollback；
  - `ReadyQueues`：priority calendar、EDF、local/global routing、steal round；
  - `TimerQueue`：register、cancel、due collection、next wake 和 shutdown cancellation；
  - `RuntimeMetrics`：record hooks、shard ownership、snapshot；
  - `GraphExecution`：完整 Graph 状态机。
- 不要创建一组只持有 `Impl*` 并转发调用的浅包装类。

### P2：测试 seam 与公共 Interface 没有严格隔离

证据：

- [`include/astra/scheduler.hpp`](include/astra/scheduler.hpp) 仍声明 `run_test_task_on_worker`、queue size、pending count、parked workers 和 work epoch 等测试函数。
- 虽然存在 [`src/test_seam.hpp`](src/test_seam.hpp)，声明仍保留在 installed header。
- [`tests/CMakeLists.txt`](tests/CMakeLists.txt) 的通用 `astra_add_test` 给所有测试加入 `src/` include path，包括标记为 public 的测试。
- `tests/consumer/main.cpp` 直接测试 `AwaitHandshake`，把内部协议当成 package contract。
- Reaper 测试通过 `find_slot()` 获取 mutex 解锁后仍可能失效的内部裸指针，并直接调用 reset/fault injection。

建议：

1. `astra_add_public_test` 只能包含安装后的 public headers，并链接真实 static/shared library。
2. 只有 `astra_add_internal_test` 可以加入 `src/` include path和 test-only runtime。
3. 增加静态门禁：public tests 禁止 `astra::detail`、`*_internal`、`src/*.hpp`。
4. Scheduler public header 中只保留一个不完整的 test access 类型声明（如确有必要），具体测试入口定义在 `src/test_seam.hpp`。
5. Reaper 测试使用只读 `ReaperSnapshot`，不返回内部 slot 指针。
6. 将 fault injection 抽成内部依赖；生产使用无故障 Adapter，测试使用 scripted Adapter，因此该 seam 有两个真实实现。
7. 深化 Module 后，用新 Interface 测试替换旧白盒测试，不要在旧测试上再叠一层包装。

### P2：Public header 组织造成额外耦合

证据：

- `coroutine.hpp` 同时包含 Task/Promise、resume invoker、handshake、TaskHandle/GraphRun awaiter、yield、sleep 和 Graph coroutine node 集成。
- `graph.hpp` 声明 `TaskGraph::emplace_coroutine`，但其定义位于 `coroutine.hpp`。
- `scheduler.hpp` 包含 coroutine、graph、task handle 以及大量模板 Implementation。

建议：

- 将公共 Coroutine 表面按依赖方向重新组织：
  - `task.hpp`：`Task<T>` 与 promise 所需最小定义；
  - `task_handle.hpp`：稳定结果 capability；
  - `coroutine.hpp`：公开 awaitables；
  - Graph/Coroutine 集成由依赖 `Task` 的一侧拥有，避免跨 header 补定义。
- 每个 public header 显式包含自己直接使用的标准库类型，不依赖传递 include。
- 将 template support 与用户主要 Interface 分开，但 template support 仍不得暴露可调用的状态控制入口。

## 5. 推荐目标结构

建议目标关系如下：

```text
Public Interface
├── Scheduler
├── TaskHandle<T>
├── Task<T> / built-in awaitables
├── TaskGraph / FrozenTaskGraph / GraphRun
├── FinalizationControl
├── Metrics/Trace snapshots
└── Options/Capabilities/IDs

Compiled Runtime Implementation
├── RuntimeState
├── AdmissionController
├── ReadyQueues
├── TimerQueue
├── RuntimeMetrics
├── TaskControlBlock
├── GraphExecution
└── ReaperService

Internal seams
├── ReadyPublisher
│   ├── Scheduler adapter
│   └── deterministic in-memory test adapter
├── RuntimeFaultPlan
│   ├── production no-fault adapter
│   └── scripted test adapter
└── TestAccess / immutable snapshots
```

Public Interface 不应出现 `TaskSharedStateBase`、`TaskInvokerBase`、`CoroutineResumeInvokerModel`、`AwaitHandshake`、mutable Graph node storage 或 Scheduler 测试函数。

## 6. 分阶段迁移顺序

### 阶段 0：治理与版本边界

1. 记录本审查结论到 Decision Ledger。
2. 明确现有 `detail`、`_internal`、`AwaitHandshake` 是否属于已承诺公共 Interface。
3. 修订 Spec 中 R-078、R-093、R-110 相关规则。
4. 修复 API freeze 和 immutable manifest 策略。
5. 决定使用 1.1 兼容过渡还是 v2 移除误暴露入口。

### 阶段 1：关闭明显逃逸口

1. 私有化 `FrozenTaskGraph::NodeData/nodes_internal()`。
2. 私有化 TaskHandle 内部构造和 shared-state accessor。
3. 私有化 Task raw coroutine handle/release。
4. 私有化 GraphRun callback registration，删除未使用的 internal accessor。
5. 从 installed `scheduler.hpp` 移除测试函数声明。
6. 分离 public/internal tests 并新增禁止内部依赖的门禁。

### 阶段 2：收敛 Task Runtime bridge

1. 引入 Runtime-owned TaskId allocator。
2. 引入 admission transaction/lease。
3. 建立 compiled `TaskControlBlock`。
4. 将 Metrics、Timer、resume route 收敛到少量 Runtime hooks。
5. 目标是显著减少 `astra::detail` 默认可见符号，而不是简单给现有 57 个符号改名。

### 阶段 3：深化 Graph Module

1. 建立 `GraphExecution`。
2. 迁移 `Scheduler::run_impl()` 的依赖传播和 terminal publication。
3. 将 `GraphRunSharedState` 字段私有化。
4. 建立 Scheduler 与内存测试两个 ReadyPublisher Adapter。
5. 用 Interface 测试替换内部状态测试。

### 阶段 4：拆解 Scheduler::Impl

1. 先抽 AdmissionController、TimerQueue、RuntimeMetrics。
2. 再抽 ReadyQueues，保持既有 memory-order 与 parking 测试证据。
3. 保持 Runtime lifecycle/Reaper handoff 的单一所有权模型。
4. 每次只迁移一组完整不变量，并保留 rule-to-test traceability。

### 阶段 5：整理 public headers

1. 重排 Task/Coroutine/Graph header 依赖方向。
2. 删除传递 include 假设。
3. 重建 public declaration manifest、header self-containment 和 package consumer tests。

## 7. 验收指标

封装改造不应只用“文件变短”评价。建议使用以下可验证指标：

- installed headers 中不再出现可调用的 runtime/test 控制入口；
- `astra::detail` 动态导出符号从当前 57 个显著下降，并有明确分类；
- public tests 无 `src/` include path、无 `astra::detail`、无 `_internal` 调用；
- FrozenTaskGraph 无法由调用方修改内部节点或 invoker；
- TaskHandle 只能由 Scheduler/Runtime 创建；
- TaskId 只由 Runtime State 分配；
- Graph 的 dependency release、cancel propagation、terminal report 可通过单一 Module Interface 测试；
- 修改 Timer、Graph 或 Metrics 规则时，不需要同时编辑多个无关 public headers；
- API freeze 允许 private Implementation 和注释变化，同时仍能阻止真实公共 Interface 破坏；
- static/shared、GCC/Clang、sanitizer、stress、package consumer 与 release gate 继续在 WSL/Linux 通过。

## 8. 风险与注意事项

- 当前已经发布 `v1.0.0`，移除普通调用方可见的方法可能构成 source breaking change；必须先明确 documented/unsupported surface 并采用已批准版本策略。
- 将 inline Implementation 移入 compiled library 会改变导出符号和 shared build 行为，不能只更新 golden 而不更新版本与迁移说明。
- Task/Coroutine 模板无法完全隐藏所有类型相关代码；目标应是把 policy、状态机、identity、Metrics 与生命周期隐藏，而不是追求零模板 Implementation。
- Scheduler、Graph、Reaper 均涉及并发不变量。迁移必须以现有 rule、ADR、Ticket 和测试证据为约束，避免通过新 Module 静默改变 memory ordering 或 shutdown semantics。
- 新 seam 只有在存在两个真实 Adapter 时才建立；纯 in-process 逻辑优先直接合并进深 Module。

## 9. 本次审查验证

- 当前 API freeze gate 在 WSL/Linux 通过：17 个 installed headers、131 个导出符号与当前 golden 一致。
- 该结果只证明当前仓库与当前 golden 自洽，不证明 golden 正确区分了公共 Interface 与内部 Implementation。
- 本审查没有修改运行时代码，也没有覆盖工作区中已有的未提交内容。
