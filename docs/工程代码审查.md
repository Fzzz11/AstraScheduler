# AstraScheduler 工程代码审查

状态：审查完成并已复核，建议未实施（涉及行为变更的条目须先修订 decision ledger）  
日期：2026-08-31

## 1. 审查范围与方法

- **代码范围**：`include/astra/` 全部 16 个公共头文件；`src/` 全部 37 个源文件（task / graph / scheduling / runtime / lifecycle / observability 六个模块）；根 `CMakeLists.txt`；`.github/workflows/ci.yml`；`tools/` 工具集。
- **方法**：逐文件通读，以代码事实（文件 + 行号）为证据，不复述 Spec 承诺作为结论。
- **参照物**：与《封装性改进建议》《src目录与Scheduler模块化优化方案》互补——本文聚焦封装之外的工程性：CI、正确性诚实度、重复、并发脆弱点、工具链。

## 2. 总体结论

AstraScheduler 的设计质量与注释质量在同类项目中属上乘：规范追溯编号贯穿全部代码、强异常安全事务、故障注入 seam、seq_cst oracle 差分验证、缓存行对齐的 metrics 分片都已就位。当前工程性短板集中在三类：

1. **验证设施与代码能力不匹配**：本地 sanitizer/测试体系完善，但 CI 只跑 Python 规则审计，不编译、不测试。
2. **少量"报告与事实不符"的诚实性问题**：`capabilities()` 上报的队列后端与实际实现不一致；普通图节点未按规范分配真实 TaskId，却为复用 Metrics 接口临时拼装 TaskId。
3. **重复与脆弱细节**：四组大段平行重复代码、Coroutine gauge 记账缺口、递归取消传播、Metrics shard 归属不准确与魔法数字。

### 2.1 复核判定摘要

| 条目 | 复核结论 | 说明 |
|---|---|---|
| P0-1 CI 不编译、不测试 | **真实存在** | CI 只有 Python release gates；但原文测试数量和“零新增成本”表述不准确。 |
| P0-2 `capabilities()` 虚报 lock-free | **真实存在，且违反 Spec** | 实际 Local Queue 为 mutex + `std::deque`，却可能上报 `ChaseLevLockFree`。 |
| P0-3 图节点拼装 TaskId | **部分真实** | 拼装行为和 ID 语义违规存在；该 ID 当前只用于 Metrics 的 Runtime 路由，尚未进入 Trace，原文所述已发生 Metrics/Trace identity 撞号缺少证据。 |
| P1-1 四组重复代码 | **真实的维护性问题** | 四组重复均存在，但 shutdown 两条路径存在注销 Reaper 等语义差异，不能机械合并。 |
| P1-2.1 gauge 竞态 | **现象真实，原诊断不准确** | 可确认的直接缺陷是 `record_metrics_resumed()` 无调用，导致 `suspended_tasks` 在 quiescent point 也可能不归零；不能仅由 check-then-act 断言并发下必然漂移。 |
| P1-2.2 取消级联递归 | **真实存在** | 递归深度随链式取消传播长度增长，图节点数又没有明确上限。 |
| P1-2.3 fallback shard 吞错 | **原判断错误** | index 越界且 Metrics 启用时会进入 control shard，不会进入 fallback；实际可疑点是外部线程默认 index 为 0，可能误写 worker 0 shard。 |
| P1-2.4 admission 释放分散 | **真实的设计风险** | 释放点分散，但当前审查没有证明已经发生重复释放或 slot 泄漏。 |
| P2-1 魔法数字 | **事实成立** | 属于可维护性和调优治理问题，不是已发生的正确性缺陷。 |
| P2-2 clang 工具链缺失 | **事实成立** | 属于工程治理缺口。 |
| P2-3 Doxygen 化 | **事实成立但可选** | 无 Doxygen 标签不等同于无法生成文档，是否实施取决于 API 文档发布目标。 |

## 3. 已有良好基础（保持不动）

- 构建边界清晰：`CMakeLists.txt` 的平台检查、`-Werror`、`-fvisibility=hidden` + version script、ExactVersion package 兼容策略、sanitizer 开关互斥。
- `tools/` 门禁体系（`check_api_freeze`、`check_encapsulation`、`check_hardening`、`check_release_gates` 等 9 个脚本）。
- 故障注入文化：`ReaperRegistry` 的 reservation/coordinator/worker 失败注入、`ChaseLevDeque` 的扩容失败注入与测试索引钩子。

## 4. 主要发现与建议

### P0-1：CI 不编译、不测试（最大工程缺口）

**证据**：`.github/workflows/ci.yml` 仅有一个 job `release-rule-gates`（第 8–21 行），只执行 `python -X utf8 tools/check_release_gates.py`。全仓库没有一个 CI 步骤执行 C++ configure/build/ctest。

**影响**：本地 WSL 验证依赖个人自觉；ASan/UBSan/TSan 证据只存在于本机构建目录（`build/wsl-gcc-asan` 等），不能由 CI 在每次提交上自动复现和形成回归门禁。合并破坏编译或引入数据竞争无法被自动发现。

**建议**：新增三个 CI job（GitHub runner 为 Linux，符合 R-111）：

1. GCC / Clang Debug + `ctest` 全量（当前 `ctest -N` 注册 53 个测试；`tests/` 根目录有 50 个 `.cpp` 测试源文件、51 个普通文件）。
2. `ASTRA_ENABLE_SANITIZERS=ON` 与 `ASTRA_ENABLE_TSAN=ON` 各一轮——开关与互斥检查已在 `CMakeLists.txt` 第 41–53 行就绪，接入代码成本较低，但仍需承担 CI 时长、运行器资源与 TSan 稳定性成本。
3. coverage（llvm-cov / gcovr）报告，作为后续测试盲区量化的基线。

### P0-2：`capabilities()` 存在"虚报 lock-free"

**证据**：

- `src/runtime/scheduler.cpp:1180-1187`：`LocalDequeBackend` 由 `detail::ChaseLevDeque<void*>::is_lock_free()` 的**编译期属性**决定上报值；
- `src/runtime/ready_queues.hpp:86-95`：实际每 worker 本地队列 `LocalQueues` 是 `mutable std::mutex` + 4 条 `std::deque`，Chase-Lev deque 未被任何 ready-queue 路径引用；
- `include/astra/capabilities.hpp:36-38` 注释承诺"绝不为了好看而虚报 lock-free"。

**影响**：调用方依据 `capabilities().lock_free_local_deque()` 做性能归因时会得到与事实相反的结论——这正是该 API 声明要防止的事情。`ChaseLevDeque` 生产实现与 oracle 验证是真实资产，但目前是"备而未用"。

**建议**（二选一，先在 decision ledger 立项）：

- 方案 A：将 `ReadyQueues` 本地带真正切换到 Chase-Lev（需解决单 owner LIFO 与 4 优先级带 + 日历轮转模型的冲突，可能改为"Chase-Lev 只承载 Normal/无 deadline 快路径"）；
- 方案 B（低成本）：将上报改为 `Locked`，并在 `capabilities.hpp` 注释与 spec 中记录"Chase-Lev 已验证、尚未接线"的现状。

### P0-3：普通图节点未分配真实 TaskId，并为 Metrics 拼装临时 TaskId

**证据**：`src/graph/graph_execution.cpp:310`：

```cpp
const TaskId metric_id{self->runtime_.runtime_identity(), index};
```

普通图节点用 `RuntimeId + NodeId` 拼装 TaskId 传给 Metrics hook，而协程节点已正确走 `allocate_graph_task_id()`（同文件第 195 行）。普通节点没有把该临时 ID 保存进 Graph 状态或报告。

**复核结论**：拼装行为确实旁路了 `TaskId` 的“由 Runtime 分配、单调递增、永不复用”契约（`id.hpp`，以及 Spec R-100/R-115），属于真实的规范偏差。不过当前这些 Metrics hook 只读取 `id.runtime_id()` 来定位 Runtime Metrics，并不保存 sequence，也不发出 Trace；因此原审查所述“当前指标与 Trace 已经发生 identity 撞号”没有代码证据，`trace_export.cpp:201-213` 也不在这条调用链上。更深层的问题是普通图节点根本没有获得规范要求的真实 TaskId。

**建议**：先明确普通 Graph Node 的身份模型并修订 decision ledger/Spec。若继续要求“完整运行节点关联为 GraphRunId + NodeId + TaskId”，普通节点应在 Graph admission transaction 中分配真实 TaskId，并进入需要该身份的 Trace/报告；若这些 Metrics hook 只需要定位 Runtime，则应改收 `RuntimeId`，不要用伪造 TaskId 充当路由参数。不能只把第 310 行替换成一次临时分配，否则可能改变 `accepted_task_identities`、失败回滚和 ID 消耗语义。

### P1-1：四组大段平行重复代码

| 重复点 | 位置 | 规模 |
|---|---|---|
| helping 等待循环 | `scheduler.cpp:735-900`（task 版）与 `scheduler.cpp:902-1052`（graph 版） | 各约 120 行，逐行平行，仅目标谓词不同 |
| 关停 join + 发布 Stopped | `scheduler.cpp:273-323`（`shutdown_sync`）与 `scheduler.cpp:395-430`（`reaper_cleanup_and_join`） | Leader-Waiter 协议完全同构 |
| coordinator join-in-progress 块 | `reaper_registry.cpp` 行 278–297、332–346、353–371、382–403 | **同一块重复 4 次**，改一处漏三处风险最高 |
| 提交事务骨架 | `scheduler.hpp:203-482` 四个 `*_impl` 模板 | admission + 强异常安全事务 ~80% 相同 |

**建议**：

- helping 循环抽成一个以"目标完成谓词"参数化的模板 helper，两版各保留差异部分；
- 关停抽取共享的 join/Stopped 发布核心，但保留 `shutdown_sync()` 的 Reaper 注销等路径差异；join 必须继续在锁外执行，避免使用容易暗示持锁 join 的 `finish_shutdown_locked()` 命名；
- reaper 的 join 块提取为 `try_join_exited_coordinator_locked()` 单一函数；
- `submit_impl` 族抽出"admission → 构造 ResultCell/invoker → 异常回滚 → 投递"公共骨架，四个入口只保留差异（options 解析、返回 variant 还是抛出）。

### P1-2：并发正确性的脆弱细节

1. **Coroutine gauge 存在确定的记账缺口，check-then-act 写法脆弱但不能单独证明漂移**：`runtime_diagnostics.cpp` 多处使用 `if (gauge.load() > 0) fetch_sub(1)`（如行 93–95、111–113、141–143、287–289、296–298）。这些是 atomic 操作，不构成 C++ data race；在每次 decrement 都有先行 increment 且状态迁移唯一的前提下，也不能仅凭该写法断言“并发下必然漂移”。但当前 `record_metrics_suspended()` 会增加 `suspended_tasks`，对应的 `record_metrics_resumed()` 却没有任何调用点，resume 直接进入 `record_metrics_resume_segment()`，因此一次正常 suspend/resume 后 `suspended_tasks` 也可能在 quiescent point 不归零。ADR-0038 已经把运行中 snapshot 定义为 fuzzy，但同时要求 quiescent point 守恒，所以仅补“近似 gauge”文档不能修复该问题。建议先补齐状态迁移记账，再将 decrement 封装为单一、可审计的饱和/守恒操作。
2. **取消级联递归**：`graph_execution.cpp:223-248` `trigger_successors` 对被取消的后继递归调用自身。十万节点链式图整体取消会递归 10 万层，存在栈溢出风险。建议改显式队列（BFS 展开），复杂度不变。
3. **Metrics shard 归属判断不完整，而不是 fallback shard 吞错**：`runtime_metrics.cpp:20-29` 在 worker index 有效时返回 worker shard，越界且存在 `control_shard` 时返回 control shard，只有 control shard 不存在时才返回 `static fallback_shard`。Metrics 启用时 `init()` 会创建 control shard，因此“worker index 越界静默写 fallback”不成立。实际需要审查的是 `t_current_worker_index` 默认值为 0，而 `shard_for_current()` 只检查 index、不检查当前线程是否属于该 Runtime Worker，外部/control 调用可能被误记到 worker 0 shard。建议以明确的 producer/worker context 选择 shard，并把 fallback 保留为不可达防御或诊断失败路径。
4. **admission 释放对账分散**：`release(1)` 散布在 worker 领取（`worker_loop.cpp:98/210`）、两套 helping 领取（`scheduler.cpp:851/1005`）、`cancel_unstarted`（`ready_queues.cpp:257/277`）及包装入口。分散所有权是真实维护风险，但当前审查没有证明已发生重复释放或 slot 泄漏。任务 slot 在“首次领取或启动前 Terminal”时释放，生命周期不同于 Graph admission lease，不能机械复用 `GraphAdmissionLease`；建议让 ReadyQueues 的 claim/cancel 结果或专用 `TaskAdmissionLease` 明确承担一次性释放责任，并用守恒测试证明行为不变。

### P2-1：魔法数字提为命名常量或配置

| 值 | 位置 | 说明 |
|---|---|---|
| 自旋 16 | `worker_loop.cpp:143` | park 前自旋次数 |

均为调参敏感值，建议提为 `constexpr` 命名常量；spin/poll 类若证明影响性能语义，再评估进 `SchedulerOptions`（注意保持"options 只暴露稳定 policy"的既有原则）。

### P2-2：工具链配套缺失

- 仓库根**无 `.clang-format` / `.clang-tidy`**（全仓库搜索仅第三方 googlebenchmark 目录内有）。53 个源文件风格靠人肉维护。
- 建议：补 root 级 clang-format + clang-tidy 配置（重点启用 `bugprone-*` 与 `concurrency-*` 检查族），并接入 P0-1 新增的 CI job；可选 pre-commit 将 `tools/check_encapsulation.py` 等门禁前置化。

### P2-3：公共头文件注释 Doxygen 化（可选）

`include/astra/` 头文件的中文注释质量很高（含设计取舍与追溯编号），但无 `@brief/@param` 标记。若目标是可安装发布的库，补 Doxygen 标记 + CI doc job 成本低、收益明确；纯内部项目可暂缓。
